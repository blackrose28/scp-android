# SCP Mobile (Android)

Kotlin + Jetpack Compose app that opens an interactive SSH shell through the gomobile
binding `scpmobile.aar`. Two routes: direct TCP (`DialDirect` → `OpenShell`) and Boundary
(`StartOidc`/`Poll` login, then `DialBoundary` → `OpenShell`).

## Build

Requires JDK 21 and the Android SDK (platform 37, build-tools 37; `sdk.dir` in `local.properties` or `ANDROID_HOME`).

```sh
cd app
./gradlew :app:testDebugUnitTest   # JVM unit tests (no device, no native library)
./gradlew :app:assembleDebug
```

The AAR is consumed from `app/app/libs/scpmobile.aar` (`scpmobile-sources.jar` alongside it documents
the API); `go/build-aar.sh` writes there by default. Rebuild it after any Go API change.

ABIs:

- **Release** ships `arm64-v8a` only (default AAR build, `defaultConfig` `abiFilters`). The release APK is
  arm64 only even if the AAR also contains x86_64.
- **Debug** also packages `x86_64` (`debug` build type `abiFilters`) so it runs on x86_64 emulators. That needs
  a dual-ABI AAR: `SCP_TARGETS=android/arm64,android/amd64 go/build-aar.sh`. With an arm64-only AAR the
  x86_64 filter is a no-op and the app can only run on arm64 devices.
- The emulator exercises the Go networking and UI, not arm64 code paths; do a final check on an arm64
  device before releasing.

## Layout (`app/src/main/kotlin/run/scp/mobile/app`)

- `tofu/` – trust-on-first-use: `FileKnownHostsStore` (keyed by the server's real `host:port`),
  `TofuHostKeyDecider`. Unknown or changed keys need an explicit decision and are persisted only when
  accepted; timeouts and UI failures reject. A changed key is shown as a warning, not auto-accepted.
- `terminal/TerminalBuffer` – small line-oriented renderer (CR/LF/BS/TAB, cursor left/right, erase in
  line; other escapes dropped). **Full-screen programs (vim, htop) are not supported yet.**
- `session/` – `SessionViewModel` owns one shell, the Boundary login, the TOFU prompt and the terminal
  snapshot; shell I/O runs through an ordered per-connection queue off the main thread. `ShellConnector`,
  `BoundaryAuthenticator` and `BoundaryLogin` are the seams that keep this testable without the native
  library. `SshTarget.route` is `Route.Direct` or `Route.Boundary(controllerUrl, authMethodId, targetId)`;
  `host:port` stays the host-key alias on both routes.
- `ssh/` – `OpenShellConnector` (AAR adapter over the `ScpBackend` seam; closes the Boundary session when
  the shell closes or fails to open), `NativeBoundaryAuthenticator` (`StartOidc`/`Poll`) and
  `KeystoreDeviceIdentity` (Ed25519 key generated by the AAR, stored AES-GCM-encrypted under an Android
  Keystore key; the public line is shown on the connect screen for `authorized_keys`).
- `backup/` – `BackupParser` (decrypted payload → servers, Boundary settings, OIDC secrets; skips malformed
  servers with warnings), `ServerEntry.connectTarget` (server → `SshTarget`/`Route`, or why it is unavailable),
  `BackupDecryptor` (AAR `DecryptBackup`) and `readBounded`.
- `servers/` – `ServersViewModel` (saved list + import flow: pick, decrypt, preview, apply, with a stale-result
  guard), `FileServerRepository` (app-private `servers.json`, atomic writes, no secrets) and `serverRows`.
- `secure/` – `Sealer`/`KeystoreSealer` (AES-GCM under an Android Keystore key) and `SealedFileSecretStore`
  (the imported OIDC password / OTP secret, never plaintext on disk).
- `ui/` – Server list, Import, Connect (Direct / Boundary toggle), Login, Connecting, TOFU and Terminal screens (Compose).

### Backup import

Servers screen → *Import backup* → pick the `.scpbak` file from the desktop app → passphrase → preview →
*Replace servers*. Tapping a server connects with the right route. Boundary servers use the controller and
auth method from the backup; only OIDC auth is supported. The OIDC password and OTP secret are stored
encrypted and used by the automated login (below). Test vectors live in `testdata/` (see its README).

### Boundary route

Servers imported from a backup carry their Boundary settings. The manual connect screen takes the controller
URL, OIDC auth method ID (`amoidc_…`) and target ID (`ttcp_…`) by hand, plus the server's real SSH host, port and user. Connecting runs
`StartOidc`, opens the IdP URL in the system browser (plain `ACTION_VIEW`, http/https only), polls until the
login finishes, then dials the target. The browser flow needs no deep link: the IdP calls back to the
controller and the app only polls. Tokens are kept in memory only (not yet Keystore-persisted), reused while
more than a minute from expiry, and dropped after any failed Boundary connect so the retry logs in again.
Login times out after 5 minutes.

**Automated login** (`oidcLoginMode: automated` in the backup, like the desktop app): the IdP page loads in an
invisible `WebView` (`login/`, `ui/AutoLoginScreen`) and a fill script ported from the desktop
`boundary_oidc_init_script` types the username, password and a fresh TOTP (SHA-1, 6 digits, 30 s, from the OTP
secret) once a second; the app keeps polling the controller as in the browser flow. Credentials are typed only into
https pages on the IdP or controller host, at most 2 password and 2 OTP submissions are made (a rejected login must
not be retried forever), the `WebView` cookies are cleared on entry and exit, and "Use browser instead" (or the retry
cap) hands the same pending login to the browser. Without a stored password or username, or with a non-https
sign-in page, the browser is used and the screen says why. Limitations: the IdP form must be in the top-level page
(not an iframe) and on the IdP's host; unlike the desktop, TOTP uses the phone clock without an HTTP-`Date` skew
correction. Verified on an x86_64 emulator against the live controller over the VPN (up to the SSH host-key prompt).
